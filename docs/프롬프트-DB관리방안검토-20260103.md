# AI 분석 프롬프트 DB 관리 방안 검토

## 1. 개요

현재 `server/csa/aiwork/prompt.py` 파일 내에 하드코딩된 Python Dictionary(`PROMPTS`) 형태로 관리되고 있는 프롬프트를 Neo4j DB로 이관하고, 클라이언트(Web)에서 관리자가 직접 수정할 수 있도록 기능을 개선하는 방안에 대한 검토 보고서입니다.

## 2. 현황 분석

### 2.1 현재 구조

- **저장소**: `server/csa/aiwork/prompt.py` 파일 내 `PROMPTS` 변수 (In-Memory Dictionary)
- **접근 방식**: `get_prompt(name)` 함수를 통해 동기적으로 조회
- **사용처**: `AIAnalyzer` 클래스의 async 메서드(`analyze_class_async` 등) 내부에서 호출됨
- **문제점**:
  - 프롬프트 수정 시 서버 코드 수정 및 재배포(재시작) 필요
  - 런타임에 프롬프트 튜닝 불가능
  - 이력 관리 및 권한 제어 불가

## 3. 구현 방안 및 타당성 검토 (Feasibility)

### 3.1 DB 모델링 (Neo4j)

- **Node Label**: `:AiPrompt`, `:System`
  - Neo4j 관례에 따라 Label로 구분 (`:AiPrompt:System`)
- **Properties**:
  - `name`: 프롬프트 식별자 (예: `class_doc`, `sql_doc`) - **Unique Key**
  - `content`: 프롬프트 텍스트 (Markdown 및 Template 변수 포함)
  - `description`: 프롬프트 설명 (옵션)
  - `updatedAt`: 수정 일시
  - `updatedBy`: 수정자 ID

### 3.2 서버 사이드 로직 (핵심 고려사항)

**가장 중요한 기술적 이슈: Async/Sync 불일치 및 성능**

- 현재 `AIAnalyzer`의 메서드들은 `async`로 동작하지만, `get_prompt`가 호출되는 시점은 `await` 되지 않는 동기 코드 블록입니다.
  
**해결 방안: In-Memory Caching 전략**

1. **Startup 시점 (Web & CLI 공통)**: 앱 초기화 시 Neo4j에서 모든 프롬프트를 로드하여 메모리(`PROMPTS` dict)에 캐싱
2. **Runtime 조회**: `get_prompt` 함수는 DB를 조회하지 않고 메모리 캐시를 반환 (기존 성능 유지 + Non-blocking)
3. **Update 시점**: 관리자가 프롬프트 수정 API 호출 시 -> **DB 업데이트** 및 **메모리 캐시 동시 갱신**

### 3.3 CLI 지원 검토 (추가)

- **실행 환경**: CLI는 Web Server와 별도의 프로세스로 실행됨.
- **적용 방안**:
  - CLI 엔트리포인트(`cli/main.py`)에서도 **초기화 시점에 프롬프트 로딩 함수(`initialize_prompts()`)를 호출**하도록 구현.
  - 이를 통해 CLI 실행 시점 기준의 최신 프롬프트를 DB에서 가져와서 분석에 사용함.
  - **주의**: CLI 실행 중에 Web에서 프롬프트가 변경되더라도 실행 중인 CLI 프로세스에는 반영되지 않음 (일반적인 CLI 동작 방식이므로 문제 없음).

### 3.4 클라이언트 (Frontend)

- **메뉴 위치**: 관리자 개요 > AI 분석 프롬프트 관리 (관리자 권한 필수)
- **기능**: 목록 조회, 상세 편집(Textarea), 저장 기능을 제공

## 4. 실행 가능성 및 예상 문제점 (Risk Assessment)

### 4.1 초기 데이터 마이그레이션 (Bootstrap)

- **해결**: `prompt.py`의 기존 내용을 **Default/Fallback Data**로 유지. 서버/CLI 시작 시 DB에 해당 키의 프롬프트가 없으면 자동 Insert 수행.

### 4.2 데이터 일관성

- **단일 인스턴스**: 문제 없음.
- **CLI vs Web**: 서로 다른 프로세스이므로 공유 메모리가 아님. CLI는 항상 "실행 시점"의 DB 데이터를 사용하므로 논리적 정합성 확보됨.

### 4.3 프롬프트 템플릿 검증

- **해결**: 프롬프트 저장(Update) 시, 필수 변수(Placeholders)가 포함되어 있는지 **유효성 검증(Validation) 로직**을 API에 추가.

## 5. 단계별 구현 계획 (제안)

### Step 1: Backend Model & Repository

1. `Prompt` 엔티티 및 Service 로직 구현 (CRUD + Cache Init)
2. `prompt.py` 수정: `initialize_prompts()` 함수 추가 및 `PROMPTS` 동적 할당
3. `cli/main.py`: 시작 시 `initialize_prompts()` 호출 추가

### Step 2: API Development

1. REST API (`GET`, `PUT`) 구현
2. 프롬프트 템플릿 검증 로직 추가

### Step 3: Frontend Development

1. 관리자 페이지 UI 구현 (React)

## 6. 결론

- **구현 가능성**: **높음**
- **CLI 지원 여부**: **지원 가능** (초기화 로직 공유를 통해 완벽 지원)
- **추천 방향**: 관리자 기능은 Web에서 수행하고, CLI는 DB의 최신 프롬프트를 읽어와서 사용하는 구조로 진행.

## 7. 구현 결과 (Implementation Results)

(2026-01-03 업데이트)

제안된 아키텍처(In-Memory Caching 전략 등)에 따라 백엔드 및 프론트엔드 구현이 완료되었습니다.

### 7.1 Backend Implementation

- **AiPrompt Model**: `server/csa/models/entities/ai_prompt.py`에 Neo4j 노드 구조 정의 (`:AiPrompt:System`).
- **AiPromptService**: `server/csa/services/ai_prompt_service.py`에 구현됨.
  - `initialize_prompts()`: 서버 시작 시 DB 로드 및 캐시 초기화, DB가 비어있을 경우 `prompt.py`의 Default Prompt로 자동 Seeding.
  - `get_prompt()`: 메모리 캐시를 통한 Non-blocking 조회.
  - `update_prompt()`: DB 저장 및 메모리 캐시 동기화.
- **Initialization**:
  - Web Server: `server/app/main.py`의 startup event에서 초기화.
  - CLI: `server/csa/cli/main.py` 진입점에서 초기화.

### 7.2 API Implementation

- **Endpoints**: `server/app/api/v1/endpoints/ai_prompts.py`
  - `GET /api/v1/ai-prompts/`: 전체 목록 조회.
  - `GET /api/v1/ai-prompts/{name}`: 상세 조회.
  - `PUT /api/v1/ai-prompts/{name}`: 프롬프트 수정 (관리자 전용).

### 7.3 Frontend Implementation

- **UI Page**: `client/src/pages/admin/AiPromptManagement.tsx`
  - 프롬프트 목록 조회 (Table View).
  - 상세 편집 및 저장 (Markdown Editor View).
- **Routing**: `client/src/App.tsx`에 `/admin/ai-prompts` 라우트 추가.

### 7.4 Verification Note

- 서버 재시작 시 자동으로 초기 프롬프트 데이터가 Neo4j에 로드되는 것을 확인해야 합니다.
- 관리자 메뉴 URL(`/admin/ai-prompts`)로 직접 접근하여 기능을 테스트할 수 있습니다.
