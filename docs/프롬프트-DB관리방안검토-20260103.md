# AI 분석 프롬프트 DB 관리 방안 검토

## 1. 개요

현재 `server/csa/aiwork/prompt.py` 파일 내에 하드코딩된 Python Dictionary(`PROMPTS`) 형태로 관리되고 있는 프롬프트를 Neo4j DB로 이관하고, 클라이언트(Web)에서 관리자가 직접 수정할 수 있도록 기능을 개선하는 방안에 대한 검토 보고서입니다.

## 2. 현황 분석

### 2.1 현재 구조

- **저장소**: `server/csa/aiwork/prompt.py` 파일 내 `PROMPTS` 변수 (In-Memory Dictionary)
- **접근 방식**: `get_prompt(name)` 함수를 통해 동기적으로 조회
- **사용처**: `AIAnalyzer` 클래스의 async 메서드(`analyze_class_async` 등) 내부에서 호출됨
- **문제점**:
  - 프롬프트 수정 시 서버 코드 수정 및 재배포(재시작) 필요
  - 런타임에 프롬프트 튜닝 불가능
  - 이력 관리 및 권한 제어 불가

## 3. 구현 방안 및 타당성 검토 (Feasibility)

### 3.1 DB 모델링 (Neo4j)

- **Node Label**: `:Prompt`, `:System`
  - 요구사항의 "System label 붙임"은 `:System` 보조 라벨을 사용하여 시스템 기본 프롬프트임을 명시하거나, `:Prompt` 노드에 `type: 'System'` 속성을 두는 방식으로 구현 가능
  - 여기서는 Neo4j 관례에 따라 Label로 구분하는 것을 권장 (`:Prompt:System`)
- **Properties**:
  - `name`: 프롬프트 식별자 (예: `class_doc`, `sql_doc`) - **Unique Key**
  - `content`: 프롬프트 텍스트 (Markdown 및 Template 변수 포함)
  - `description`: 프롬프트 설명 (옵션)
  - `updatedAt`: 수정 일시
  - `updatedBy`: 수정자 ID

### 3.2 서버 사이드 로직 (핵심 고려사항)

**가장 중요한 기술적 이슈: Async/Sync 불일치 및 성능**

- 현재 `AIAnalyzer`의 메서드들은 `async`로 동작하지만, `get_prompt`가 호출되는 시점은 `await` 되지 않는 동기 코드 블록입니다.
- 만약 `get_prompt` 내부에서 매번 DB를 조회(`session.run`)하게 되면, 블로킹 I/O가 발생하여 **이벤트 루프가 차단**될 위험이 있습니다.

**해결 방안: In-Memory Caching 전략**

1. **Startup 시점**: 서버 구동 시(또는 모듈 초기화 시) Neo4j에서 모든 프롬프트를 로드하여 메모리(`PROMPTS` dict)에 캐싱
2. **Runtime 조회**: `get_prompt` 함수는 DB를 조회하지 않고 메모리 캐시를 반환 (기존 성능 유지 + Non-blocking)
3. **Update 시점**: 관리자가 프롬프트 수정 API 호출 시 -> **DB 업데이트** 및 **메모리 캐시 동시 갱신**

### 3.3 클라이언트 (Frontend)

- **메뉴 위치**: 관리자 개요 > AI 분석 프롬프트 관리
- **권한 제어**: 메뉴 진입 및 API 호출 시 `administrators` 그룹 체크 필수
- **기능**: 목록 조회, 상세 편집(Textarea), 저장 기능을 제공

## 4. 실행 가능성 및 예상 문제점 (Risk Assessment)

### 4.1 초기 데이터 마이그레이션 (Bootstrap)

- **이슈**: 최초 실행 시 DB에 프롬프트 데이터가 없을 수 있음
- **해결**: `prompt.py`의 기존 하드코딩된 내용을 **Default/Fallback 데이터**로 유지. 서버 시작 시 DB에 해당 키(`name`)의 프롬프트가 없으면 자동으로 Insert 하는 **Seed 로직**이 필요함.

### 4.2 데이터 일관성

- **이슈**: 다중 프로세스(Gunicorn 등) 환경에서는 한 프로세스에서 캐시를 갱신해도 다른 프로세스에 반영되지 않음
- **현황**: 현재 사용자의 환경은 단일 로컬 워크스페이스/단일 프로세스 환경이므로 큰 문제는 없으나, 추후 확장 시 Redis 등을 고려해야 함. 현 단계에서는 **단일 인스턴스 기준 In-Memory 캐싱**으로 충분함.

### 4.3 프롬프트 템플릿 검증

- **이슈**: 프롬프트 내부에 `{sql_content}` 등의 Python f-string 포맷팅 변수가 포함되어 있음.
- **위험**: 사용자가 실수로 `{}` 변수를 삭제하거나 잘못된 이름을 사용하면 런타임 에러(`KeyError`) 발생 가능.
- **해결**: 프롬프트 저장(Update) 시, 필수 변수(Placeholders)가 포함되어 있는지 **유효성 검증(Validation) 로직**을 API에 추가해야 함.

## 5. 단계별 구현 계획 (제안)

### Step 1: Backend Model & Repository

1. `Prompt` 엔티티 정의 (Pydantic 모델 아님, Neo4j 노드 구조 정의)
2. `PromptService`: DB 조회, 저장, 초기화(Bootstrap) 로직 구현
3. `prompt.py` 수정:
   - `PROMPTS` 변수를 동적으로 초기화하는 로직 추가
   - 초기화 함수(`initialize_prompts()`)를 앱 시작 시점에 호출

### Step 2: API Development

1. `GET /api/v1/prompts`: 목록 조회
2. `GET /api/v1/prompts/{name}`: 상세 조회
3. `PUT /api/v1/prompts/{name}`: 수정 (Validation 포함)
4. 권한 체크 Decorator 적용 (`@require_admin` 등)

### Step 3: Frontend Development

1. `Administration` 관련 라우트에 페이지 추가
2. API 연동 및 UI 구현 (React Hook Form 활용 권장)

## 6. 결론

- **구현 가능성**: **높음**
- **기술적 난이도**: **중** (캐싱 전략 및 초기화 로직 필요)
- **추천 방향**: 성능 저하를 방지하기 위해 **Startup Loading + In-Memory Caching** 방식을 반드시 채택해야 하며, 사용자 실수 방지를 위한 **템플릿 변수 검증**이 필수적임.
