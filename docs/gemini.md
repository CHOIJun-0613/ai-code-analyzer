# Antigravity Global Rules

## 1. 기본 행동 및 커뮤니케이션 (Behavior & Communication)
- **언어 원칙:** - 모든 대화(Conversation), 계획(Plan), 설명(Walkthrough), 주석(Comment)은 **한국어**로 작성한다.
  - 단, 코드의 변수명, 함수명, 클래스명 등 프로그래밍 식별자는 문법적으로 정확한 **영어**를 사용한다.
- **아키텍처 존중:** - 기존 프로젝트의 폴더 구조와 디자인 패턴을 분석하고 이를 준수한다.
  - 임의로 파일 위치를 옮기거나 구조를 변경하지 않는다. 구조 변경이 필수적인 경우, 명확한 근거와 함께 제안한다.
- **신중한 접근 (Think First):**
  - 코드를 수정하기 전에 **<생각하기>** 단계와 **<영향도 분석>** 단계를 거친다.
  - 수정이 미칠 파급 효과(Side Effect)를 고려한 후, 수정 계획을 나에게 먼저 브리핑하고 **승인(Confirm)**을 받는다.
- **변경 이력 명시:**
  - 코드 수정 후에는 "어떤 파일이, 왜, 어떻게 변경되었는지" 요약하여 텍스트로 보고한다.

## 2. 모듈화 및 코드 품질 (Modularity & Code Quality)
- **함수(Function) 작성:**
  - **단일 책임 원칙(SRP):** 하나의 함수는 하나의 기능만 수행하도록 설계한다.
  - **길이 제한:** 함수 본문은 가급적 **100줄 이내**로 유지한다. 100줄이 넘어가면 내부 로직을 하위 함수(Sub-function)로 추출한다.
- **파일(File) 작성:**
  - **관심사 분리:** 파일 크기가 커지면 단순히 쪼개는 것이 아니라, 도메인, 기능, 역할에 따라 논리적으로 분리한다.
  - **길이 제한:** 하나의 소스 파일은 **1000줄 이내** 유지를 권장한다. 초과 시 별도의 모듈/클래스로 분리하고 Import하여 사용한다.
- **네이밍 컨벤션:**
  - 해당 언어(Java, Python 등)의 표준 Style Guide(PEP8, Google Java Style 등)를 준수한다.

## 3. 주석 및 문서화 (Comments & Documentation)
- **작성 원칙:** 코드를 생성하거나 수정할 때, **의도(Intention)**와 **이유(Why)**를 설명하는 주석을 필수적으로 작성한다.
- **Docstring:** - 클래스와 퍼블릭 함수(Public Method)에는 반드시 Docstring을 작성한다.
  - Docstring 포맷은 언어별 표준을 따른다 (예: Python의 Google Style Docstring, Java의 Javadoc).
- **언어:** 모든 주석과 문서는 **한국어**로 작성하여 가독성을 높인다.

## 4. 안정성 및 에러 처리 (Stability)
- **방어적 코딩:** 입력값 검증과 예외 처리를 누락하지 않는다.
- **삭제 주의:** 파일 삭제나 기존 로직의 대규모 제거가 필요한 경우, 반드시 재확인을 요청한다.
